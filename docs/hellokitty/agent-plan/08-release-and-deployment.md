# Этап 08 — собственный релиз, staging и развёртывание

Статус реализации этапа: **NOT RUN**. Собственные release keys, signed release, OTA origin, production backend и ingress пока не созданы/не развёрнуты. [Debug APK и проверки очистки](../app-cleanup.md) не считаются production release. Текущая просьба пользователя — подготовить документы для другого агента; она не разрешает публикацию, развёртывание или изменение рабочих сервисов.

## Цель и результат

Подготовить проверяемый самостоятельный release Hello Kitty VPN, source/SBOM/provenance, собственные signing/update origins и безопасный deployment bundle. После отдельного разрешения на конкретное production действие — провести контролируемый rollout с реальными health/payload checks и откатом. Результат подготовки можно полностью проверить до публикации: локальные артефакты, подписи, конфигурация, resource budget, diff и runbook.

## Входы и блокеры

- Gates [01](01-contracts-and-security.md)–[05](05-ru-routing-and-networking.md) и [07](07-pilot-and-hardening.md). Этап [06](06-vk-whitelist-transport.md) требуется лишь если release включает VK. Непрошедший VK остаётся disabled/experimental; regular VPN можно выпускать отдельно после собственных gates.
- Человеческие решения: владельцы домена/репозитория/distribution account, страна/ASN exit, budget/пропускная способность, release capability scope, Direct и Play signing identity strategy, хранение/backup ключей, собственный VK-account при включении relay. Отсутствующие входы перечисляются как blockers; local build policy/templates/source review выполняются независимо.
- Для Play отдельно: собственный publishing account, package ownership, privacy disclosure и требуемая Play configuration/integrity policy. Если этого нет — Direct-only release, не подставлять чужой cloud project и не отключать validation для зелёной сборки.
- `versionName=0.1.0`, исторический `versionCode=69`, package `org.hellokittyvpn.android`, debug suffix `.debug` — состояние после очистки. Релизная sequence/versionCode выбирается один раз и далее монотонна. Старые Levik ключи/аккаунты/API origins не использовать.
- Рабочее дерево содержит выполненную ранее очистку. **Не clean/reset/stage/commit чужие или текущие изменения без явного разрешения.** Сохранить tree/diff snapshot, построить reviewable local artifacts. Для immutable published source требуется отдельно утверждённая собственная revision/content snapshot и identity; нельзя приписать dirty build чистому upstream HEAD.

## Инварианты релиза и развёртывания

1. APK signing, OTA manifest signing, profile/API signing, routing signing и node mTLS/HMAC — разные ключи/назначения/`keyId`. Private keys не в Git, CLI arguments, logs и SBOM. Секреты передавать root-only regular files/approved secret mounts, минимальным пользователям; процессы/temporary files чистятся проверяемо.
2. Direct updater до настроенного и проверенного собственного origin остаётся disabled. Собственный API/update/rules endpoint в release config явно задан; `.invalid` placeholder, Nort321 origins и старый support URL не могут оказаться активным fallback. Не включать generic redirect-to-GitHub policy.
3. OTA сохраняет существующие криптографические проверки: ECDSA P-256/SHA256, strict DER, signed manifest bytes, APK SHA256/size/package/version/signer certificate pin, allowlisted HTTPS origin, bounded redirects/download. Expired/tampered/downgrade/wrong certificate отклоняются. Manifest key ротация — подписанный прежним доверенным key transition + overlap, не blind trust нового JSON key.
4. Source provenance содержит фактический application source state, exact Xray/libXray/relay commits, patchset/lock/hash, toolchains, dependencies, build flags и artifact checksums. Повторная native-сборка проверяет byte equality где воспроизводимость достигнута; где она не достигнута — явно причины и signed provenance, не ложное «reproducible».
5. AGPL/GPL/LICENSE/NOTICE/provenance не удалять при ребрендинге. Noncommercial статус не заменяет source obligations. Corresponding-source bundle покрывает приложение, изменения, закреплённый native source, используемые modules/patches, build/install scripts; сетевой AGPL backend должен предоставлять применимое предложение исходников. Использование чужих trademarks/assets оценивается владельцем отдельно от технической лицензии исходников.
6. Play и Direct подписываются по заранее выбранной стратегии, с проверкой update path. Если release package общий, разные сертификаты не позволяют бесшовно менять flavor; не обещать cross-flavor update без доказанной signing lineage/strategy. Debug package отдельный, его нельзя обновлять production APK поверх автоматически.
7. Один API ingress и Reality/Xray не могут одновременно bind один IP:443 без отдельного согласованного ingress design. Control hostname и отдельный зарубежный exit IP/node предпочтительнее. Node agent/admin/DB/metrics не публичные. Public listener inventory — обязательный gate.
8. Deploy topology/ports/resource limits не затрагивают соседние projects. Current shared server не считается выделенным: initial inventory Ubuntu24.04/x86_64, RAM≈15GiB, available≈8GiB, nearly full2.5GiB swap, free disk≈22GiB — исторический снимок, повторить до выполнения. Исходно nginx80/8443, чужой WDTT UDP56000, Xray10808/10809 и другие порты заняты.
9. `127.0.0.1:18080` API, `127.0.0.1:19090` metrics, relayUDP56010, exitTCP443 — **кандидаты**, не зарезервированные/проверенные сейчас значения. DB без published5432, node agent только management network/loopback. Проверять TCP/UDP и Docker networks/subnets отдельно, A/AAAA/provider ACL внешне с authorized probes.
10. Текущий relay pool249 records с 24h leases и retained tombstones48h остаётся admission limit, не рекламной ёмкостью пользователей. Production caps задаются stage07 measurements плюс reserve для renewal/rotation/retention. Повышение pool/хранилища — новый engineering change, не параметр ради обхода gates.

### Волны

- **A, главный + 3 workers:** release source/tooling audit, read-only host/topology inventory и независимый security/source/distribution review. Согласовать public metadata и immutable source policy; отсутствие keys не тормозит templates/tests.
- **B, главный + 2 owners + reviewer:** release tooling адаптируется локально, deploy bundle строится в disposable staging, reviewer готовит tamper/install checks. CPU/RAM budget и serialized Gradle соблюдаются.
- **C:** локальные signing/source/build/install tests и staging restore/rollback. Нельзя одновременно запустить тяжёлый native build, Docker load и Gradle на shared host без измеренного ресурса. General security checks после окончательной конфигурации выполняет независимый reviewer.
- **D:** главный показывает владельцу concrete changes/artifact hashes/commands/affected domains and ports/rollback/limitations; если нужный внешнему действию input или разрешение отсутствует, production остаётся NOT RUN. Вопрос не задаётся заранее вместо подготовки.
- **E:** после явного разрешения один operator выполняет только reviewed apply, поэтапные probes и rollout; остальные наблюдают независимые diagnostics, не параллельно меняют firewall/DB/ingress.

## Release manifest и конкретные действия

### A. Собственные инструменты и цепочка доверия

1. Проаудировать существующие `.github/workflows/android-release.yml`, `android-publish.yml`, `android-feed-refresh.yml` и `scripts/release/levik-android-release-*`. В них исторические owners/paths/artifact names/remote operations; они **ещё не адаптированы и не запускались как Hello Kitty release**. Их defaults должны fail-closed до own repo/environment/keys/config и разрешённого publish.
2. Согласованно обновить `scripts/ci/check-android-release-workflow.sh`: сегодня он требует литерал `Nort321/levik-vpn`; после адаптации он должен требовать собственный allowlisted repository и запрет старого origin. Сохранить action SHA pins, permission минимизацию, immutable tag/source gate, signing validation, checksum/source/SBOM и разделение build vs publish. Нельзя просто удалить policy script или убрать обязательные проверки.
3. `scripts/release/build-corresponding-source.sh` требует clean tracked source/committed HEAD, exact AAR checksum и anet source. Нынешний dirty checkout не удовлетворяет release gate: не reset и не commit автоматически. Подготовить проверяемую diff/source inventory и определить разрешённую immutable revision; либо отдельно реализовать явно утверждённый content-addressed snapshot pipeline, включающий все modified/untracked исходники, с digest вместо ложного upstream commit. До решения bundle gate остаётся UNABLE TO RUN. `source/tools.lock`/native locks не ослаблять.
4. Адаптировать bundle/SBOM/update-feed filenames и documentation под Hello Kitty; provenance attribution upstream оставить. Зафиксировать применимые license obligations библиотеки и native executable, backend/node-agent, third-party assets. Собрать источники и build instructions, потом из source archive собрать в чистом disposable workspace и сравнить artifacts/provenance.
5. Владелец создаёт/передаёт собственные Direct/Play signing keys и отдельный OTA P-256 key через approved private storage; agent пишет scripts/public metadata и backup/runbook, не публикует private keys. Проверить `hkvpn.*`/`HKVPN_*` inputs, `validateDirectReleaseSigning`, `validatePlayReleaseSigning`, `validateDirectReleaseOtaConfiguration`, current certificate SHA256. Отсутствующие keys означают NOT RUN signed build, не fallback debug key.
6. Настроить собственный release endpoint и только затем сменить disabled updater на собственный manager. Network policy запрещает чужой mirror/redirect и mixed HTTP. Signed feed cache имеет monotonic version и expiry; offline last-known artifact допускается только по policy/verified hashes. Не скачивать обязательный executable runtime после установки: cached connection должен иметь packaged native components.

### B. Сборка, размер и установка

1. Проверить pinned AAR через `bash scripts/ci/fetch-libxray.sh`, relay через штатные source/build scripts, Gradle locks и strict verification. Для будущего release выполнить `testDirectReleaseUnitTest`, `testPlayReleaseUnitTest`, `lintDirectRelease`, `lintPlayRelease`, `verifyDirectReleaseRuntimeClasspath`, `verifyAllDependencyLocks`, затем `assembleDirectRelease` и условный `bundlePlayRelease`; actual task names сверить `./gradlew tasks --all`. Checks ожидают присутствия keys/config там, где нужны; не выключать gates.
2. Current build поддерживает `-Phkvpn.abiFilters=arm64-v8a` и соответствующие validated ABI. Измерить R8 release size: full Direct universal и per-ABI arm64/armv7/x86_64, Play AAB device downloads. Debug размеры примерно134MiB Direct/210MiB Play не являются target мобильного релиза. Согласовать release download/install budget по измерениям; APK label/architecture/memory/disk требований должны быть понятны пользователю.
3. Подтвердить ELF type/linker/API26/16KiB LOAD alignment для relay и всех packaged shared libraries, а также ZIP/native packaging и Android16KiB page device. Alignment scanner не заменяет фактическую установку и startup на 16KiB device. Source/AAR native pin подтверждается hashes; CPU ABI mismatch имеет ясную ошибку выбора APK.
4. Запустить `apksigner verify --verbose --print-certs` для APK, Play bundle metadata validator для AAB после собственных inputs, hash/size manifest, SBOM (`cyclonedxDirectBom` и соответствующий Play task по actual Gradle) и native SBOM generator. Локально проверить signed update manifest/provenance, не ограничиваться наличием `.sig` файла.
5. Install matrix: Android8/API26, Android13, Android16, 16KiB page-size device, arm64/armv7/x86_64 при заявлении поддержки; clean install, upgrade собственной предыдущей версии с тем же signer, per-ABI update, Direct↔Play policy, revoked VPN permission, locked boot, limited disk/RAM, download interruption, damaged cache, noGMS Direct. Native startup, VPN consent, own-profile payload и offline cached connect обязательны; только launch screen не достаточно.
6. Подписанный source/SBOM/checksum/provenance комплект выдаётся вместе с APK по own origin после publish authorization. Play publish отдельно условный; его отсутствие не мешает корректному Direct-only candidate.

### C. Staging и ops bundle

1. Read-only preflight: `ss -lntup`, Docker ps/networks, resource/disk/NTP, kernel/cgroup/IPv6, own DNS A/AAAA и provider filters; чужие secrets/configs не читать. Обновлённый inventory записать timestamp. Проверить disk forecast images/build artifacts/backups/logs, не считать full swap резервом.
2. `deploy/compose.yaml`: отдельный project prefix, pinned image digests, private bridge, scoped volumes, non-root/minimal capabilities where possible, secrets mounts, read-only filesystem/tmpfs где совместимо, restart policies, readiness/healthchecks. API/worker первоначально256–512MiB каждый, DB≈1GiB, control budget≤2GiB — стартовый бюджет после повторного inventory; реальные caps stage07, node отдельно. FD/pids/CPU/log limits без доступа к соседней Docker socket.
3. Local isolated staging не означает public production: loopback API/metrics, DB internal без host ports, disposable identities/certificates/volumes, dedicated subnet без collisions. `docker compose config` валидирует syntax, но не доказывает network readiness, startup order или capacity; проверять actual health/contract/payload и restart.
4. Предварительно подготовить own nginx server block/TLS и API/exit ingress design, `nginx -t` в isolated config. Existing global nginx/firewall/SSH/NTP не менять в подготовке. Из старого `levik_whitelist_relay/deploy/test-vps/` брать только проверенные идеи после адаптации; его IP/secret paths/distro units/nftables полный ruleset не применять на shared server.
5. Dedicated firewall/egress ACL: только own ingress ports, management agent/Xray gRPC закрыты; preserveSSH, private/reserved/metadata deny IPv4/IPv6 после DNS resolution; Docker publish bypass учесть. Production firewall patch ограничен own chains и до apply имеет diff, secondary SSH session и rollback. Time-sync correction специфична host distribution, не blind replacement chrony lines.
6. Secret/cert rotation staging: node mTLS SAN identity, HMAC keyId overlap/replay semantics, profile/routing/OTA key purpose isolation. Отзыв compromised key не компенсировать widened time window. Initial owner enrollment/invitation CLI local-only, public admin UI/unauthenticated proxy не добавлять.
7. Backup/restore/rollback scripts запускаются только на own staging names и требуют явный target; валидируют paths/regular files/permissions, не shell interpolation input. Restore в отдельную DB, reconcile revoked/expiry прежде issuance. Off-host encrypted backups/independent storage, alert disk/outbox/readiness/signature/expiry; retention: technical logs7d, no-device aggregates30d, admin audit90d как initialpolicy; payload/tokens/URLs не писать.

## Negative/security/fault проверки

| Тест | Дефект, который должен обнаружить | Gate evidence |
|---|---|---|
| Tampered manifest/APK/provenance, wrong key/signer/package/size | Trust основан на HTTPS или filename вместо signed artifact | Verified rejection до install; existing APK/profile intact |
| Old feed/downgrade/wrong clock и new untrusted keyId | Rollback/re-key позволяет установить старый вредоносный build | Monotonic/trusted transition policy соблюдена; TLS verification не выключена |
| Own origin 302 к Nort321/unknown CDN/HTTP | Origin allowlist обходит redirect | Credentials/файл не отправлены/получены вне разрешённого origin |
| Different ABI/16KiB/Android8 + native executable start | Build alignment правильный, runtime linker/extraction несовместим | Установка и actual tunnel startup на заявленной матрице |
| Direct↔Play или signer mismatch upgrade | Пользователю обещан невозможный update path | Signing lineage/certificate evidence либо явный отказ с безопасной migration guidance |
| Dirty source archive omits untracked cleanup files | Published APK не соответствует предлагаемому source | Clean snapshot/content digest + rebuild comparison; ни один modified source не потерян |
| Secret marker в env/argv/logs/source/SBOM | Release automation раскрывает signing/VK/API material | Marker absent в all outputs; secret files permissions/cleanup verified |
| Agent/gRPC/DB/metrics reachable from external namespace | Compose publish/Docker firewall открыл control plane | External negative probe rejected; only approved ingress exposed |

| Backup restore + version rollback | Старое desired state возвращает revoked credentials | Stage07 recovery scenario после restore/rollback пройден |

## Gates, review и production sequence

**G08-A — local candidate:** source state immutable и accurately identified; release tooling адаптирован; required keys/config доступны или blocked явно; unit/lint/dependency/security/build/install/native/source/license/OTA tests выполнены. Warnings и несовпадение воспроизводимости перечислены, а не скрыты. Не использовать debug evidence как release test.

**G08-B — staging operations:** own compose/topology/ports/limits/secrets/ACL проверены, real authenticated payload работает, renewal/revoke/restart/restore/rollback пройдены, stage07 caps применены. Широкие unreachable cells и VK limitation отражены в release notes/UI/capability gating.

**G08-C — внешнее действие:** главный предъявляет владельцу готовый diff, точные artifact/image hashes, source/provenance, target hostnames/ports/resources, resource impact, DB migration/backup evidence, команды apply и rollback, remaining limitations. Публикация APK/исходников, открытие public ingress, DNS/cloud changes, production deploy и Play upload требуют отдельной точной авторизации, если она ещё не дана для этих действий. В рамках текущего docs-only запроса gate остаётся NOT RUN; сейчас confirmation не спрашивать.

После G08-C: backup текущего own state → apply compatible DB migration → API/worker/node readiness → private synthetic lifecycle/payload/revoke → только own ingress patch и config validation → external TLS/ACL/reachability проверка → малый authorized pilot → 10%/25%/100% **доступной согласованной аудитории** при заранее утверждённых error/resource thresholds. Проценты — схема rollout, не созданные группы; без enrollment count использовать фиксированные batches. Initial alarm candidates: oldest outbox>60s, disk<15%, RSS>80% утверждённого limit, confirmed-cell payload failures>5%; окна/минимальную выборку и action согласовать по stage07 measurements. Остановить rollout сразу при critical leak, auth/revoke/restore corruption, false CONNECTED или exceeded budget. Signing/publish и backend deploy можно выполнять раздельно; не публиковать APK, который требует отсутствующий backend.

## Откат и handoff

Откат deployment: остановить новые issuance/worker writes при необходимости, сохранить existing permitted sessions, вернуть previous compatible image/ingress/rules, проверить DB schema compatibility и revoked state. APK version rollback через OTA не bypass anti-downgrade: исправленная совместимая версия с большим versionCode либо documented owner-operated recovery. Compromised credential/key отзывается, даже если это оборвёт сессию. Запрещены global firewall flush, `docker compose down -v`, удаление чужих volumes и переиспользование foreign secrets.

`docs/hellokitty/execution/S08-report.md` содержит: **VERIFIED / FAILED / NOT RUN / UNABLE TO RUN** по каждому gate; own source revision/content digest; artifact/image/native hashes/ABIs/page-size evidence; signer certificate fingerprints и public keyIds; source/SBOM/license locations; actual install matrix; exact own origins/ports/limits без private secrets; snapshot inventory timestamp; staging restore/rollback timing; human blockers и scope of authorization; production executed commands/health evidence только если они действительно выполнены. Финальный handoff разделяет готовый локальный candidate, проверенный staging и реально развернутый production, а также regular и experimental VK capabilities.
